# Masterplan v1.0 비판적 리뷰 결과 (r2 — 확장 컨텍스트 반영)

## Context

`docs/masterplan-draft-r1.0.md` (Knowledge Evolution Engine 설계 문서 v1.0)을 6개 관점에서 심층 분석한 결과.

### 프로젝트 전체 범위 (r2 업데이트)

| 항목 | r1 가정 | r2 실제 |
|------|---------|---------|
| 대상 도서 | 경제학 책 1권 | **87권** (인문, 사회, 역사, 경제, 과학, 기술, 경영) |
| 스케일 전략 | 단일 책 완결 | **1권 MVP → 87권 확장** |
| 핵심 애플리케이션 | 지식 구조화 | **콘텐츠 생성 + 비즈니스/콘텐츠 아이디어 창출** |
| 생성 기능 | 부차적 | **MVP 핵심 요구사항** (API 또는 내장) |
| 지식 진화 | 닫힌 시스템 | **웹 크롤링 + 편집으로 외부 지식 흡수** |

> **r1 리뷰의 핵심 비판이었던 "1인+1권 규모 불일치"가 해소됨.** 87권 멀티도메인이라면 마스터플랜의 상당 부분이 정당화된다. 아래는 이 새로운 컨텍스트에서 재평가한 결과.

## 1. 프로젝트 목표: 달성 가능한가?

### 선언된 4가지 목표 재평가

| # | 목표 | r1 판정 | r2 판정 | 근거 |
|---|------|---------|---------|------|
| 1 | 콘텐츠 제작 백본 | ⚠️ 조건부 | ✅ **달성 가능** | 87권 × 도메인 7개 = 풍부한 소재 풀. 생성 기능이 MVP에 포함되면 즉시 활용 가능 |
| 2 | 비즈니스 아이디어 생성 엔진 | ❌ 비현실적 | ✅ **핵심 목표로 격상** | 7개 도메인 교차점에서 아이디어 발견이 구조적으로 가능. LLM 사전 지식 의존 문제도 87권 KU가 구체적 컨텍스트를 제공하면 완화 |
| 3 | 도메인 간 지식 연결 | ⚠️ 장기적으로만 | ✅ **본질적 강점** | 7개 도메인이 이미 확보됨. 경제×기술, 역사×경영 등 cross-domain 연결이 시스템의 차별화 가치 |
| 4 | 진화 구조 (외부 지식 + 피드백) | ❌ 비현실적 | ⚠️ **조건부 달성 가능** | 웹 크롤링으로 외부 지식 유입 경로 확보. 다만 Usage-driven maturation의 임계치(검색 20회 등)는 여전히 재조정 필요 |

### 핵심 판단 변화

r1에서의 "기업급 시스템을 개인 프로젝트에 적용"이라는 비판은 **87권 멀티도메인에서는 유효하지 않다.** 87권 × 평균 150 KU = **약 13,000개 KU**로, 이 규모에서는:
- Hybrid Search(Vector + Graph)가 실질적 가치를 가짐
- Cross-domain 연결이 수천 개 edge를 생성하여 Graph Traversal이 의미 있음
- Usage-driven maturation도 콘텐츠 생성 과정에서 자연스럽게 데이터 축적 가능

**그러나 여전히 유효한 비판:** MVP 단계에서 87권 전체를 한번에 처리하려 하면 안 된다. 1권 → 5권 → 87권의 점진적 확장이 필수.

## 2. 구현 방법은 목표에 정렬되어 있는가?

### r1의 "과잉 설계" 판정 재평가

| 설계 요소 | r1 판정 | r2 판정 | 근거 |
|----------|---------|---------|------|
| **L3 Dispute Axis** | 과잉 | ⚠️ **Phase 2에서 정당화** | 87권 다저자 환경에서 상충 주장 풍부. 예: 경제학 vs 경영학의 시장 효율성 견해 차이. 단, 1권 MVP에서는 여전히 불필요 |
| **L4 Evolution (PR 모델)** | 과잉 | ⚠️ **간소화 필요하나 방향 유효** | 웹 크롤링 결과를 기존 KU에 병합하는 메커니즘 필요. PR 모델보다는 "자동 제안 + 수동 승인" 패턴이 적절 |
| **Usage-Driven Maturation** | 과잉 | ⚠️ **임계치 재조정 필요** | 콘텐츠 생성 + 아이디어 탐색이 핵심 용도이므로 사용 데이터가 자연 축적됨. 단, 임계치를 현실적으로 낮춰야 (검색 5회, 사용 2회 등) |
| **Hybrid Search** | 과잉 | ✅ **13,000 KU 규모에서 필수** | Vector만으로는 cross-domain 탐색 한계. Graph Traversal이 "경제학의 X 개념과 연결된 기술 분야 KU"를 찾는 데 핵심 |
| **FastAPI + Next.js** | 과잉 | ⚠️ **생성 기능 요구 시 재검토** | 생성 기능(콘텐츠 + 아이디어)이 MVP 핵심이라면, API 서버가 필요할 수 있음. 단, Next.js 프론트엔드는 여전히 MVP에 과잉 — CLI/API 우선 |

### 새로운 정렬 문제: 생성 기능의 위치

마스터플랜 v1.0은 생성 기능을 부차적으로 취급하지만, 새 컨텍스트에서는 **두 가지 핵심 애플리케이션 중 하나**다:

1. **콘텐츠 생성**: KU 기반 블로그/뉴스레터/교육 콘텐츠 자동 초안
2. **아이디어 생성**: Cross-domain KU 조합으로 비즈니스/콘텐츠 아이디어 탐색

이 두 기능은 마스터플랜에서 명시적 설계가 부족하다. 생성 파이프라인(KU 선택 → 프롬프트 조합 → LLM 호출 → 결과 저장)이 별도 모듈로 설계되어야 한다.

## 3. 각 구현 단계는 적절히 분리되고 자족적인가?

### 레이어 의존성 재분석 (87권 컨텍스트)

```
L0 (Raw)     ← 독립적. 자족적 ✅
L1 (KU)      ← L0에만 의존. 자족적 ✅
L2 (Graph)   ← L1에 의존. 자족적 ✅ (87권이면 cross-domain edge 풍부)
L3 (Dispute) ← L2에 의존. ⚠️ 5권+ 이후 자족 가능 (1권에서는 여전히 불가)
L4 (Evolution) ← L1-L3 + 웹 크롤링. ⚠️ 웹 크롤링 인프라 구축 후 자족 가능
```

### r1에서 유효했던 문제와 현재 상태

1. **L3-L4 자족성 문제** — ⚠️ **부분 해소.** 87권이면 L3가 의미 있으나, MVP(1권)에서는 여전히 공허. Phase 설계에서 L3 활성화 시점을 "5권 이상 등록 후"로 명시해야.

2. **Waterfall Phase 구조** — ❌ **여전히 문제.** 87권 처리를 위해서는 오히려 더 반복적(iterative) 접근이 필요:
   - 1권 완전 처리 → 검증 → 파이프라인 안정화 → 배치 처리(5권) → 전체 확장
   - Phase 1/2/3 순차 실행은 87권 규모에서 리스크가 더 커짐

3. **Hybrid Search 위치** — ⚠️ **규모가 커지면서 독립 모듈로 분리 정당화.** 13,000 KU에서는 검색이 핵심 기능이므로 별도 서비스로 분리하는 것이 합리적.

### 새로운 문제: 생성 레이어 부재

현재 L0-L4 아키텍처에 **생성(Generation) 레이어가 없다.** 제안:

```
L0 (Raw)       — 원본 텍스트
L1 (KU)        — 구조화된 지식 단위
L2 (Graph)     — 관계 그래프
L2.5 (Gen)     — 생성 파이프라인 (콘텐츠 + 아이디어) ← 신규 필요
L3 (Dispute)   — 논쟁 축 (Phase 2)
L4 (Evolution) — 웹 크롤링 + 지식 진화 (Phase 3)
```

## 4. 구현 가용성 (비용 + 기술)

### 비용: 87권 규모 재산정

| 항목 | 1권 (MVP) | 87권 (Full) |
|------|-----------|-------------|
| LLM API (KU 추출) | $2-15 | **$170-1,300** |
| 임베딩 (text-embedding-3-small) | $0.03 | **$2-3** |
| 웹 크롤링 인프라 | $0 | **$0-10/월** |
| DB (Supabase Free → Pro) | $0/월 | **$0-25/월** (Free로 시작, 필요시 업그레이드) |
| 총 초기 비용 | **$2-15** | **$170-1,300** |

**비용 전략:**
- MVP(1권)는 여전히 $2-15로 충분
- 87권 전체는 모델 선택에 따라 차이 큼: GPT-4o mini($170) vs GPT-4o($1,300)
- 점진적 처리로 비용을 분산 가능 (월 $30-50씩 10권 단위)
- **비용은 여전히 핵심 제약이 아님** — 다만 한번에 투입이 아닌 분할 투입 권장

### 기술적 실현 가능성 재평가

| 레이어 | r1 난이도 | r2 난이도 | 변경 근거 |
|--------|-----------|-----------|----------|
| L0 Raw | 쉬움 | 쉬움 | 변동 없음 |
| L1 KU | 중간 | 중간 | 변동 없음. 단, 87권 배치 처리를 위한 파이프라인 자동화 필요 |
| L2 Graph | 중-상 | **중** | 다저자 간 관계가 명시적이므로 오히려 edge 품질 향상. 동일 개념의 cross-domain 매핑이 핵심 과제 |
| L3 Dispute | 상 | **중-상** | 다저자 환경에서 상충 주장이 명시적. 단, 자동 감지보다 반자동(LLM 후보 제안 + 수동 확인)이 현실적 |
| L4 Evolution | 중 | **중-상** | 웹 크롤링 + KU 병합이 기술적으로 추가됨. 크롤링 대상 선정, 중복 감지, 품질 필터링 필요 |
| **Gen (신규)** | — | **중** | LLM API 호출 + 프롬프트 엔지니어링. RAG 패턴으로 KU를 컨텍스트에 주입 |

### 개발 시간 재추정

| 범위 | 시간 |
|------|------|
| MVP (1권, L0+L1+L2+Gen) | **1-2주** |
| Phase 2 (5-10권, L3 추가) | **2-3주** |
| Phase 3 (87권, L4+웹크롤링) | **4-6주** |
| 총계 | **7-11주** (2-3개월) |

r1의 4-6개월 추정 대비 단축 가능한 이유: 프론트엔드를 MVP에서 제외하고, CLI/API 기반으로 시작.

## 5. 더 우수한 대안 구현 방법

### r1 대안의 재평가

| 대안 | r1 평가 | r2 평가 | 근거 |
|------|---------|---------|------|
| **대안 A: Obsidian + Python** | 강력 추천 | ⚠️ **MVP로는 유효하나 확장성 한계** | 87권 × 150 KU = 13,000개 마크다운 파일은 Obsidian에서 관리 곤란. Graph View가 1,000+ 노드에서 성능 저하 |
| **대안 B: Neo4j + Python** | 보조 옵션 | ⚠️ **규모에는 적합하나 생성 기능 부재** | 그래프 DB는 13,000 KU에 적합하지만, 콘텐츠/아이디어 생성 파이프라인은 별도 구현 필요 |

### 대안 C: Python Pipeline + LLM API + 경량 DB (r2 신규 권장)

**87권 멀티도메인 + 생성 기능 핵심 요구를 반영한 새 대안:**

**구현:**
1. **Python 파이프라인**: PDF → KU 추출 → JSON/SQLite 저장 (배치 처리 가능)
2. **임베딩 + Vector DB**: 의미 검색용 (ChromaDB 또는 Supabase pgvector)
3. **생성 모듈**: KU 기반 콘텐츠/아이디어 생성 (LLM API, 프롬프트 템플릿)
4. **CLI 인터페이스**: 검색, 생성, 탐색 명령어
5. **마크다운 출력**: 생성 결과를 마크다운으로 저장 (Obsidian 호환)

**비용:** $2-15 (MVP) | **개발 시간:** 1-2주 | **커버리지:** 마스터플랜의 70%

**마스터플랜 대비 장점:**
- 생성 기능이 1등 시민(first-class citizen)
- 87권 배치 처리를 위한 파이프라인 자동화 내장
- CLI 기반이므로 프론트엔드 없이 즉시 사용
- SQLite/ChromaDB로 시작 → 필요시 PostgreSQL/Supabase 마이그레이션 용이
- Obsidian과 병행 사용 가능 (마크다운 출력)

### 권장 전략: 생성 중심 점진적 확대 (r2)

```
Week 1:     1권 MVP — L0+L1+Gen(기본) → KU 추출 + 콘텐츠 초안 생성 검증
Week 2:     L2(Graph) + Gen(아이디어) → Cross-concept 연결 + 아이디어 생성 검증
Week 3-4:   5권 배치 처리 → 파이프라인 안정화 + cross-domain 연결 검증
Month 2:    20권 처리 + L3(Dispute) 도입 → 다저자 논쟁 축 탐색
Month 3:    87권 완료 + L4(웹 크롤링) → 외부 지식 유입 + 지식 진화
Month 3+:   필요시 웹 UI 추가 (FastAPI + 경량 프론트엔드)
```

**핵심 원칙:** 매 단계에서 **생성 기능의 실제 가치를 검증**. KU만 쌓고 사용하지 않는 "지식의 묘지"가 되지 않도록.

### 마스터플랜 v1.0에 대한 최종 판단

87권 멀티도메인 + 생성 기능 핵심 + 웹 크롤링 진화라는 컨텍스트에서, 마스터플랜 v1.0의 **아키텍처 비전(L0-L4)은 건전하다.** r1에서 "과잉"으로 판정한 L3(Dispute), L4(Evolution), Hybrid Search 모두 이 규모에서는 정당화된다.

**그러나 실행 계획은 여전히 수정이 필요하다:**

1. **생성 기능 부재** — 마스터플랜의 가장 큰 결함. 콘텐츠/아이디어 생성이 핵심 애플리케이션인데 설계에 명시적 레이어가 없음
2. **Waterfall Phase 구조** — 87권을 순차 Phase로 처리하면 리스크 누적. 1권 → 5권 → 87권 점진적 확장 + 매 단계 가치 검증이 필수
3. **프론트엔드 우선순위** — Next.js는 Month 3+ 이후. MVP는 CLI/API로 충분
4. **웹 크롤링 설계 부재** — L4 Evolution이 "PR 모델"에 집중하지만, 실제 진화의 핵심은 웹에서 새 정보를 가져와 기존 KU를 보강하는 것

**권장:** 마스터플랜 v1.0을 **아키텍처 참조 문서로 격상**하되, **실행 계획(v2.0)은 "생성 중심 + 점진적 확장" 원칙으로 재설계**. 대안 C(Python Pipeline + LLM API)로 시작하여 1-2주 내에 핵심 가치 검증.
