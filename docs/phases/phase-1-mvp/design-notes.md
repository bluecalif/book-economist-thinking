# Phase 1: 1권 MVP — Design Notes
> Last Updated: 2026-02-25

## Stage A: 프로젝트 초기화

### 설계 대안 (Alternatives Considered)

| # | 대안 | 장점 | 단점 | 결정 |
|---|------|------|------|------|
| 1 | Click CLI | 성숙, 풍부한 생태계 | 보일러플레이트 많음 | 보류 |
| 2 | Typer CLI | 타입 힌트 기반, 간결 | Click 위에 추가 레이어 | **유력** |

### 열린 질문 (Open Questions)

## Stage B: DB 스키마

### 설계 대안

| # | 대안 | 장점 | 단점 | 결정 |
|---|------|------|------|------|
| 1 | SQLAlchemy ORM | 풍부한 추상화, 마이그레이션 | 과도한 추상화, 학습 비용 | 기각 |
| 2 | Raw SQL + 헬퍼 함수 | 단순, 직접 제어 | SQL 직접 작성 | **채택** |
| 3 | Peewee ORM | 경량 | 생태계 작음 | 기각 |

### 열린 질문
- [ ] edges 테이블 DDL을 Phase 1에서 미리 생성할지, Phase 2에서 생성할지 — DDL만 미리 생성 쪽으로 결정

## Stage C: PDF 파싱

### 설계 대안

| # | 대안 | 장점 | 단점 | 결정 |
|---|------|------|------|------|
| 1 | 기존 JSON만 사용 | 즉시 시작, 파싱 비용 0 | 새 책 추가 시 별도 파싱 필요 | 1차 경로 |
| 2 | PyMuPDF 직접 파싱 | 범용, 새 책 즉시 지원 | 구현 비용, 파싱 품질 검증 필요 | 2차 경로 |
| 3 | pdfplumber | 테이블 추출 강점 | PyMuPDF보다 느림 | 기각 |

### 열린 질문
- [ ] 기존 JSON의 text 필드가 챕터/페이지 단위로 구분되어 있는지 확인 필요 — C.1에서 분석

## Stage D: KU 추출

### 설계 대안

| # | 대안 | 장점 | 단점 | 결정 |
|---|------|------|------|------|
| 1 | 챕터 단위 LLM 호출 | 컨텍스트 풍부, 관계 파악 용이 | 토큰 비용 높음, 긴 입력 | 기각 |
| 2 | 페이지/단락 단위 호출 | 비용 효율, 병렬화 가능 | 문맥 단절 가능 | **채택** |
| 3 | 슬라이딩 윈도우 | 문맥 유지 + 비용 적정 | 구현 복잡 | Phase 1 후 재평가 |
